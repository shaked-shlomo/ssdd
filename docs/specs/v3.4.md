# v3.4 — findings have outcomes

**Date:** 2026-10-22, trimmed 2026-10-23, revised for v3.6 2026-10-30 · **Status:** draft (clarify pass not run) · **Branch:** none yet

## Goal

The gate loop converges. A re-review is told which findings are still open,
answers each one by ID, and never repeats one; a finding the change didn't
introduce doesn't hold the commit; a loop that keeps going says so. Today the
gate proves that a reviewer ran and keeps a count; it doesn't know what the
reviewer found, so the next round can't build on it.

**Trimmed** (owner, 2026-10-23): the first draft also blocked commits on open
findings, recorded every outcome in the commit message, and standardized
`BACKLOG.md`. The first two are deferred (Out); the third is its own spec,
`SPEC.md` → v3.5. The full draft, with its evidence for the deferred parts,
is `git show 68a02e9:docs/specs/v3.4.md`.

**Revised for v3.6** (owner, 2026-10-30): v3.6 (`SPEC.md` → v3.6) makes the
git pre-commit the only review gate and `--stamp` the only way to stamp,
and removes Claude Code's completion stamps, so SSDD works the same on any
harness. This draft read findings at SubagentStop; it now reads them from
the report `--stamp` is given. v3.4 is built on v3.6. The draft before this
revision is `git show 7d2a6a2:docs/specs/v3.4.md`.

## Decisions

1. **One outcome vocabulary.** `fixed`, `wrong` (a false positive),
   `intentional` (by design), `minor` (true, not worth the change),
   `deferred` (real; it gets a home, as `SDD.md` §3 already requires) and
   `pre-existing`. Each carries a one-line reason. The ledger's triage, the
   triage note and the reviewer contract use these words.
   - The gate sets two of them: `fixed` from a re-review (Decision 3) and
     `pre-existing` from the reviewer's tag (Decision 4).
   - The rest are the author's triage, written in the ledger or the commit
     message, as today (`SDD.md` §4 step 3). Nothing checks them; that's
     deferred (Out).
2. **Findings are parsed from the report `--stamp` is given, and belong to
   the review.**
   - `--stamp <reviewer> --report <file>` reads the reviewer's final text
     from the file (`-` for stdin). It parses the verdict line and each `❌`
     and `⚠️` line into an ID, reviewer, kind, cited `path:line` and text.
     The orchestrator saves each reviewer's reply as it comes back; that's
     the only new step, and it's the same on every harness.
   - A report with no verdict line is refused with the reason, so the
     orchestrator can re-ask the reviewer; nothing is stamped.
   - A review is one reviewer plus the files it stamped; each stamp entry
     gains the ID of the review that wrote it. A finding can cite a file
     outside that set (resilience traces a retry owner to another file).
   - The findings sit in the stamp file next to the stamps. They're work
     state, not a record, and go stale with the stamps they belong to.
   - `--report` is optional (Open 1). A `--stamp` without it stamps as
     today, records no findings, and prints one line: the next re-review of
     those files gets the delta only, not the open findings.
   - The triage note names each open `❌` by ID on the file it cites,
     instead of copying a count onto every file. It still doesn't block.
     `--check` lists the open `❌` too.
3. **The re-review is told what's open, and says what it fixed.**
   - For a file a reviewer stamped with open findings, the block message
     gives the delta (as today), plus those findings by ID and text.
   - The reviewer contract gains one line: for each listed finding,
     `✅ [<id>] fixed` or `❌ [<id>]` (still open); never re-report one
     that's listed.
   - Only `✅ [<id>] fixed` records `fixed`. Silence leaves the finding
     open: a stamp covers every routed file the reviewer owns unless
     `--files` narrows it, whatever its input named (`SDD.md` §4 step 3), so
     silence-means-fixed would close findings on files the re-review never
     read.
   - This is the article's auto-clear and no-repeat rule, held to the
     refute-by-default standard of `SDD.md:121`.
4. **Pre-existing is a test, not a location:** the finding holds against
   HEAD's version of the code. A caller the change breaks sits on an
   untouched line and isn't pre-existing.
   - The reviewer writes `❌ [pre-existing] …`; it's recorded as
     `pre-existing`, isn't listed as open, and doesn't count toward a round.
   - A `[pre-existing]` finding that cites a line the change adds loses the
     tag. The added lines come from convention-lint's `addedLines`
     (`convention-lint.mjs:100`).
   - Moved code is the author's call: triage it `pre-existing` with the
     reason. An author who fixes one anyway gets `✅ [<id>] fixed` from the
     next review like any other.
5. **A round cap on the gate loop that warns.** It applies to the gate's
   per-file rounds, the loop that ran to 12 in prizma, not to Superpowers'
   task fix loop.
   - A round is a review by reviewer R of file F where R's previous stamp on
     F had open findings and the same HEAD-side blob. A commit or a rebase
     starts the count over.
   - At `reviewGate.maxRounds` (default 3) the block message says not to
     dispatch another round: list the open findings and ask the user whether
     to rethink the approach or triage them.
   - It's a warning, like `maxRoutedFiles` (`review-gate.mjs:285-296`), not
     a block.

## Scope

**In:**
- review-gate: the finding parse in `--stamp --report`, findings in the
  stamp file, the re-review list in the block message, the triage note and
  `--check` naming open findings by ID,
  the round count and its warning, the `[pre-existing]` added-line check.
- The five framework reviewers and the domain template: the
  `[pre-existing]` tag, `✅/❌ [<id>]` answers, no repeats.
- `SDD.md` §3 and §4 step 3, and the ledger template's triage line: the
  outcome words.
- Config: `reviewGate.maxRounds`.
- The selftests and CHANGELOG.

**Out (deferred, from the first draft):**
- **Blocking a commit on an open `❌`, with the author proposing an outcome
  and the reviewer or the user ruling** (draft Decisions 4–5:
  `--propose`, `--rule`, `--report` required in block mode).
  - It costs a step per finding and possibly a dispatch, and a proposal no
    re-review picked up would stay pending until `/cleanup`, which SSDD
    doesn't require before merge.
  - The evidence points the other way: prizma left findings unfixed "rather
    than void the file's stamps" (39:59), and silent drops had no evidence
    either way.
  - Revisit if the triage note and the parsed findings show `❌` committed
    with no triage.
- **The commit message as the record** (draft Decisions 9–11: `SSDD-`
  lines, a `commit-msg` hook, `--findings`, `/cleanup --checked`).
  - It's a second system: a new git hook, a line per unfixed finding in
    every routed commit, a public-repo switch, and about twenty open
    mechanism questions (IDs across rounds, squash, amend, the line
    grammar).
  - The smallest version, if the noise metric is wanted later, is one
    counts-only `SSDD-Review:` line.
- **A standard `BACKLOG.md` and `/migrate-backlog`:** `SPEC.md` → v3.5.
- Severity tags across all reviewers (only security rates severity today).
- A verifier agent per finding: declined in v3 Part 5 (`v3.md:2454`), and
  prizma's one majority vote dropped none of 47 findings.
- Past incident PRs as a test set; nightly sweeps of old code; the
  article's risk tiers, required approvals and merge queue.

**Footprint:** one optional flag on `--stamp` and its parse, findings in
the stamp file the gate already keeps, a few lines per reviewer, and one
config key. No new git hook, no harness hook at all, no new script, nothing
that blocks a commit. It runs the same in Claude Code, Cursor and a
terminal.

  ships first, and v3.4 builds on its gate.

  record; move the backlog standard to v3.5.
- **Harness-neutral** (2026-10-30): findings come from `--stamp --report`,
  not a Claude Code hook. The former Open 1 (`stamping: "hooks"` by
  default) is gone with hooks mode (v3.6 Decision 2).

Resolved 2026-10-30 (owner, as my call):

1. **Should `--stamp` require `--report`?** Without a report the gate
   knows nothing about findings, so the re-review list, `[pre-existing]`
   and the round cap don't apply to that stamp. Requiring it would make a
   missing report refuse the stamp, which then holds the commit: a new
   block on something that can be undone, against the owner's rule. My
   call: optional, with the one-line note (Decision 2), and revisit if the
   ledgers show stamps without reports.

## Clarify pass

*Not run.* It has to settle at least:
- The finding-line grammar: `❌`/`⚠️`, an optional `[pre-existing]` or
  `[<id>]`, the `path:line`, and security's `❌ <severity> …` form.
- What happens when the parse finds fewer `❌` lines than the verdict's N.
- The ID format. The re-review maps a listed finding to the code by its
  text, so IDs needn't survive line moves; a new finding gets a new ID.
- Where a file's round count lives in the stamp file.
- How the open findings reach the re-review on every harness: the block
  message lists them (Decision 3), and the orchestrator passes them on.
  Whether `--check` should also print them in a form to paste into the
  dispatch.
- `--report` with several reviewers in one `--stamp`: one file per
  reviewer (`--report <reviewer>=<file>`, repeatable), or one call per
  reviewer.
- Where the orchestrator keeps report files (inside `.git`, like the stamp
  file, so they're never untracked), and when they're deleted.
- Whether a review ID in each stamp entry keeps the stamp file at version 2
  (v2.3 called its fields additive).
- A finding on a file deleted or renamed between rounds.
