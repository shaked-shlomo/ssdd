# v3.4 — findings have outcomes

**Date:** 2026-10-22 · **Status:** draft (clarify pass not run) · **Branch:** none yet

## Goal

Every finding a reviewer reports gets an answer before its commit lands, and
the answers are kept so a noisy reviewer shows up as a number. Today the gate
proves that a reviewer ran; it doesn't know what the reviewer found.

## Evidence

**SSDD's gate today:**
- A stamp attests that the reviewer ran. `N ISSUE(S)` stamps like `CLEAN`;
  the only trace is a non-blocking triage note (`review-gate.mjs:211-228`).
  "Fix or triage" is a process rule (`SDD.md` §4 step 3, line 93).
- The stamp keeps a count, not findings, and copies the review's count onto
  every file the review covered (`review-gate.mjs:862`), so the triage note
  can name a file no finding was about.
- A manual `--stamp` carries no verdict and no count. In manual mode (the
  default, and Cursor's only mode) the gate knows nothing about findings.

  <staged blob>` (`deltaFor`, `review-gate.mjs:270`) but not the findings

  re-reporting one that was already triaged.

  filter later" (`docs/model-era-review.md:46,61`). At commit time the
  filter is the agent that wrote the code, and nothing records what it

- `SDD.md:121` already calls findings "structured records (finding,
  reviewer(s), severity, file)". They live only in the session: the ledger
  keeps prose triage, and a commit made without a plan has no ledger.
- Stamp data lives in `git rev-parse --git-dir` (`review-gate.mjs:117,186`),

**Outside: Anthropic, "Solving code review at Anthropic"** (claude.dev,
read 2026-10-22 through a fetched summary; their numbers, not ours):
- Open findings block merge until they're fixed or closed with a reason. A
  later commit that fixes one clears it.
- Findings carry Important, Nit or Pre-existing, so a bug the PR didn't
  introduce isn't blamed on it.
- Every comment is classified by the author's response (fixed, wrong,
  intentional, didn't matter). That and a set of past incident PRs are how
  they judge a change to the reviewer.
- One PR ran 50+ agent-on-agent review rounds overnight; about 59% of what
  kept being flagged was old code. After a 3-round cap, diff-only re-review,
  class-wide findings and no repeats, PRs passing after one round went from
  65% to 78%, five or more rounds from 8.9% to 1.5%, and mean reviews to
  pass from 2.08 to 1.32.

## Decisions

My calls, except where Open says otherwise.

1. **One record per finding, with an outcome.** The outcomes are `fixed`,
   `wrong` (a false positive), `intentional` (by design), `minor` (true, not
   worth the change), `deferred` (real; it gets a home, as `SDD.md` §3
   already requires) and `pre-existing`. Every outcome carries a one-line
   reason. Decision 5 says who may set one. The ledger's triage uses the
   same words, so there's one vocabulary.
2. **Findings come from the reviewer's final text.**
   - In Claude Code with the subagent hooks wired, the SubagentStop hook
     already reads that text for the verdict (`parseVerdict`,
     `review-gate.mjs:758`). It also parses each `❌` and `⚠️` line into
     reviewer, kind, cited `path:line` and text.
   - A manual `--stamp` takes the same text as `--report <file>` (owner,
     2026-10-22), so Cursor and manual Claude Code get the same records.
     The stamp's verdict and findings come from the report.
   - A manual report is an attestation the gate can't check, as a manual
     stamp is today (`docs/limitations.md`).
   - In block mode, a manual stamp without `--report` is refused: it would
     let every finding through unseen.
3. **Findings belong to the review, not to a file.** A finding can cite a
   file outside the reviewer's staged set (resilience traces a retry owner
   to another file). A review is one reviewer plus the files it stamped; each
   stamp entry gains the ID of the review that wrote it.
4. **An open `❌` blocks the commit.** The gate blocks a commit that stages
   a file a review covered while that review has a `❌` with no outcome and
   no pending proposal (Decision 5). The block message lists each one with
   its ID. A `⚠️` never blocks: it's
   recorded, and may get an outcome. On by default (owner, 2026-10-22);
   `reviewGate.findings: "note"` is the opt-out, and keeps today's triage
   note.
5. **The reviewer closes its own `❌`; the author only proposes.** This
   follows the owner's ask on 2026-10-22: blocking must not push agents to
   close real problems as `minor` on their own say-so.
   - `review-gate.mjs --propose <id,…> <outcome> "<reason>"` records the
     author's proposal, for any outcome. The finding stays open. A proposed
     `fixed` names where the fix is (a file or a commit): a fix in a file
     the reviewer doesn't cover is exactly that case.
   - The next dispatch of the reviewer that raised the finding gets the
     proposals along with the open findings (Decision 6), and rules on each
     one, refute-by-default.
     - `✅ [<id>] accepted` closes it with the proposed outcome,
       `by: "hook"`.
     - `❌ [<id>]`, with why the reason doesn't hold, keeps it open.
     - "Not worth it" isn't a reason unless it names the cost.
   - When the author fixes some findings and proposes the rest, the ruling
     rides with the re-review: no extra dispatch.
   - A proposal that no re-review picks up gets no dispatch of its own
     (owner, 2026-10-23). It's recorded as pending and doesn't block the
     commit. `/cleanup` checks it against the code before merge
     (Decision 11).
   - A finding the reviewer has rejected blocks until it's fixed, or until
     the user rules on it through `--rule <id> <outcome> "<reason>"`. A new
     proposal can't turn it back into pending.
     - In Claude Code, git-guard answers `--rule` with "ask", so the user
       approves it in the permission prompt, as with prod-guard's asks. It's
       recorded `by: "user"`.
     - Cursor turns an ask into a deny, so there the user runs `--rule` in a
       terminal.
   - The open findings, proposals and rulings live in the stamp file
     (Decision 9), which git-guard already protects (`git-guard.mjs:58`).
   - This is mechanical only with `reviewGate.stamping: "hooks"`, where the
     agent can't stamp and a ruling comes only from the reviewer's
     completion. In manual mode (today's default) the agent passes the
     reviewer's text through `--stamp --report`, so an accepted proposal is
     an attestation (Open 1).
6. **The re-review is told what's open, and says what it fixed.**
   - For a file a reviewer stamped with open findings, the block message
     gives the delta (as today), plus those findings by ID and the ones
     already resolved.
   - The reviewer contract gains one line:
     - for each listed open finding, `✅ [<id>] fixed` or `❌ [<id>]` (still
       open)
     - for each proposal, `✅ [<id>] accepted`, or `❌ [<id>]` with why the
       reason doesn't hold (Decision 5)
     - never re-report a resolved finding
   - Only `✅ [<id>] fixed` records `fixed`, `by: "hook"`. Silence leaves the
     finding open. A completion stamp covers every routed staged file the
     reviewer owns, whatever its input named (`SDD.md` §4 step 3). A
     silence-means-fixed rule would therefore close findings on files the
     re-review never read: a ledger row written from intention, made
     mechanical.
   - This is the article's auto-clear and its no-repeat rule, held to the
     refute-by-default standard of `SDD.md:121`.
7. **Pre-existing is a test, not a location:** the finding holds against
   HEAD's version of the code. A caller the change breaks sits on an
   untouched line and isn't pre-existing. The reviewer writes
   `❌ [pre-existing] …`, and the finding is recorded with outcome
   `pre-existing`. It doesn't block and doesn't count toward a round. An
   author who fixes it anyway (the "this task owns the file" case) proposes
   `fixed`, and the next review confirms it. The latest outcome counts.
   - One check: a `[pre-existing]` finding that cites a line the change adds
     loses the tag and blocks. The added lines come from convention-lint's
     `addedLines` (`convention-lint.mjs:100`).
   - Moved code is the exception: the author proposes `pre-existing` with
     the reason (Decision 5).
8. **A round cap on the gate loop that warns.** It applies to the gate's
   per-file rounds, the loop that ran to 12 in prizma, not to Superpowers'
   task fix loop (which has its own cap of five).
   - A round is a review by reviewer R of file F, where R's previous stamp
     on F had open findings and the same HEAD-side blob. A commit or a
     rebase starts the count over at 1.
   - At `reviewGate.maxRounds` (default 3) the block message says not to
     dispatch another round: list the open findings and ask the user
     whether to rethink the approach.
   - It's a warning, like `maxRoutedFiles` (`review-gate.mjs:285-296`),
     not a block. Pre-existing findings don't count.
9. **The commit message is the record; there's no log** (owner,
   2026-10-23).
   - While work is in progress, the open findings, proposals and rulings
     sit in the stamp file (`.git/ssdd-review-stamp.json`), next to the
     stamps. That's work state, like the stamps, not a record. It's dropped
     for a file once that file's change is committed.
   - At commit time, a `commit-msg` hook installed beside the pre-commit
     hook adds lines to the message. No AI is involved.
     - `SSDD-Review: security 2 rounds, 3 fixed; docs-sync clean`, on every
       commit that stages a routed file, clean reviews included. A clean
       run is the denominator of a reviewer's noise rate.
     - One `SSDD-Finding:` line for each finding the commit didn't fix. It
       holds the ID, the reviewer, `path:line`, the outcome, who closed it
       (or `pending`), the finding in one short line, and the reason. For
       example: `SSDD-Finding: sec-2 security api/messages.ts:40 deferred
       (BACKLOG.md) — "no login check on GET" — "fixed by the auth
       middleware, step 5"`.
     - Only a commit with no routed files gets no lines. So a routed commit
       with no `SSDD-Review:` line was made with the hooks dormant, and a
       script can tell, since the routing is in the config.
     - One line per item, each key with its `SSDD-` prefix (owner,
       2026-10-23). Dropping the prefix was tried and reverted: a body
       sentence starting "Review:" could then be misread.
   - The lines belong to the commit they describe. They survive a rebase,
     reach every machine through git, and show in the PR's commit list. A
     squash merge keeps them when its message includes the commits'
     messages (Clarify).
   - On a public repo, the finding's text and the reason are public too.
     `reviewGate.findingText: false` keeps the ID, reviewer, `path:line` and
     outcome, and drops both texts. `/cleanup` then can't check a pending
     reason in that repo, and says so.
   - Uncommitted work moved to another machine is reviewed again there, as
     its stamps already are today.
10. **`--findings` prints the report, from `git log`.**
    - It reads the `SSDD-` lines of the commits in range, so it gives the
      same counts on every machine.
    - Per reviewer: reviews, findings, outcome counts, a noise rate (`wrong`
      plus `minor` over resolved) and a rounds histogram.
    - How many of the author's proposals the reviewer rejected, how many
      `/cleanup` refuted, and how many went to the user.
    - Filtered with `--since` and `--branch`.
    - It replaces the hand comparison in `docs/usage.md:158` (new model:
      compare rounds and findings with the ledger).
    - It feeds `/new-reviewer`'s "bug classes that recur in the ledgers".
11. **`/cleanup` checks the pending proposals, and shows the author's
    dismissals.**
    - For a branch or PR, it reads the `SSDD-` lines of the PR's commits
      (`git log <base>..<head>`). They tie each finding to its PR exactly,
      with no matching on branch names.
    - It checks each pending proposal against the code it cites,
      refute-by-default. This happens in the pass `/cleanup` already makes
      over SSDD reviewers' findings (its §4). The checker is a fresh
      session, not the author.
      - Confirmed: shown with the line that proves the reason, and closed
        `by: "cleanup"`.
      - Refuted: the finding reopens and becomes an item in `/cleanup`'s
        plan.
      - It records each result with `review-gate.mjs --checked <id>
        confirmed|refuted`. That's the same channel as `--propose`: it goes
        into the stamp file, and its fix commit's `commit-msg` hook writes
        `SSDD-Checked: conv-3 confirmed` (or `refuted`).
    - It also lists the findings already closed as anything but `fixed`,
      with each one's reason and who closed it: the reviewer, `/cleanup`,
      or the user.
    - A commit with routed files but no `SSDD-Review:` line (its hooks
      were dormant) is named as such, never shown as clean.
    - SSDD doesn't gate merges. A branch merged without `/cleanup` leaves
      its proposals pending, and `--findings` lists them.
12. **Every SSDD repo has a `BACKLOG.md`, and deferred findings live in
    it** (owner, 2026-10-22: one standard file, not a path per project).
    - It sits at the repo root, beside `AGENTS.md`. `install` seeds it from
      a template when the repo has none.
    - The template is small: Now, Next, Later, Deferred review findings,
      and Done. A project may add sections of its own; the gate reads only
      finding IDs.
    - A `deferred` proposal adds a row there that carries the finding's ID.
      The gate closes the finding only when the staged `BACKLOG.md`
      contains that ID. The reviewer still judges whether it can wait
      (Decision 5).
    - This is prizma's rule, "a finding with no row here doesn't exist",
      made mechanical and general. A finding still to be fixed then reaches
      every machine through git.
    - A `pre-existing` finding worth keeping becomes a `deferred` row the
      same way. The rest are only in the commit message's lines.
    - On a public repo, a deferred security finding's row is public. It
      names the problem and where it is, never how to exploit it. The
      template says so, and so does the security reviewer's contract for
      the finding's one-line text.
    - These all become `BACKLOG.md`:
      - `SDD.md` §7's "requirements/production checklist"
      - the ledger template's Follow-ups
      - `/new-reviewer`'s "requirements checklist"
13. **A repo whose backlog has another name migrates it, and is told
    exactly what moves.**
    - `install` and `update` look for a candidate: a file at the root or
      in `docs/` named like a backlog (BACKLOG, TODO, ROADMAP,
      REQUIREMENTS…, …requirements, …checklist). When there is one, they
      don't seed over it. They name it and point to `/migrate-backlog`.
    - `/migrate-backlog` changes nothing until the user approves its
      report. The report lists:
      - the rename: the old path → `BACKLOG.md`
      - how each existing section maps onto the template, and which ones
        stay as they are
      - the rows it reformats (deferred findings into the row form), with a
        count
      - every mention of the old file it rewrites, grouped (instructions,
        reviewers, skills, plans, ledgers, audits), with a count per group
    - Afterwards, every mention points to `BACKLOG.md`, history included
      (owner, 2026-10-22). That covers:
      - paths and links
      - section anchors the reformat renames
      - short names, such as Hatedate's "REQUIREMENTS §0"
    - No stub is left at the old path, since nothing in the repo names it
      any more.
    - It lands as one commit on a branch, like `/migrate-plans`.

## Scope

**In:**
- review-gate:
  - parsing findings at SubagentStop
  - the open-`❌` block and the re-review list
  - `--check` reporting open findings as well as owed stamps
  - `--propose`, `--rule`, `--checked` and `--findings`
  - `--stamp --report` for manual mode
  - the round count and its warning
  - the `[pre-existing]` check
  - the check that a deferred finding's ID is in the staged `BACKLOG.md`
  - the in-progress findings in the stamp file
  - `--findings` reading `git log`
- The `commit-msg` hook that writes the `SSDD-` lines, and the installer
  arming it beside pre-commit.
- git-guard: `--propose` allowed in hooks mode, `--rule` answered with
  "ask".
- The five framework reviewers and the domain template: the
  `[pre-existing]` tag, answers by ID on open findings and proposals, no
  repeats.
- `SDD.md` §3 (the outcome words) and §4 step 3; the ledger template's
  triage line.
- `/cleanup` §4: checking pending proposals against the code, and listing
  the branch's non-`fixed` outcomes.
- `BACKLOG.md`:
  - the template, and a row for it in the AGENTS template's Documentation
    Map
  - the installer seeding it, or naming a candidate file instead
  - `/migrate-backlog`, a new skill
  - `SDD.md` §7, the ledger template and `/new-reviewer` naming it
- Config: `reviewGate.findings`, `reviewGate.maxRounds`,
  `reviewGate.findingText`.
- The selftests, CHANGELOG, and `docs/limitations.md` (manual mode).

**Out:**
- Severity tags across all reviewers (Important / Nit). Only security rates
  severity today; adding it is a separate call.
- A verifier agent per finding: declined in v3 Part 5 (`v3.md:2454`), and
  prizma's one run of a majority vote dropped none of 47 findings.
- Past incident PRs as a reviewer test set; nightly sweeps of old code. The
  `pre-existing` records are the input a sweep would want later.
- Risk tiers, required human approval, a merge queue, flags: the article's
  machinery for its scale.

**Footprint.** Part 5 cut SSDD down to what it does. This adds:
- one parse, where the text is already read
- four modes, a `--report` flag and three config keys
- one "ask" in git-guard
- one git hook, `commit-msg`, which writes only the commit's own message
- a few lines per reviewer
- a step in §4 and a paragraph in `/cleanup`
- the `BACKLOG.md` template and one skill, `/migrate-backlog`

There's no new script and no new harness hook event, and no log: the only
new state outside the commit is in the stamp file the gate already keeps.

## Open

  author proposes and the reviewer or the user decides (Decision 5).

  - Neither project has completion stamps today: prizma runs a forked gate,
