# v3.6 — the gate costs what its threat model buys

**Date:** 2026-10-30 · **Status:** draft (clarify pass not run) · **Branch:** none yet

## Goal

A review round costs a reviewer only when the code it reviewed changed, and
a commit costs one call. The 2026-10-23 audit found the gate charging extra
rounds and tool calls for things outside its threat model ("the hooks keep a
cooperating agent on the process; they aren't a sandbox", `docs/BACKLOG.md`).
The owner's rule for this release: a hard block stays only where a mistake is
irreversible or outward-facing; everything else warns or goes.

**SSDD stays harness-neutral** (owner, 2026-10-30: "it should still be a
general framework that fits any harness chosen", Cursor included). Every
rule in v3.6 lives in git or the CLI, so Claude Code, Cursor, Codex or a
human at a terminal gets the same gate. A harness hook may make a check
earlier or cheaper; it never adds a rule of its own. v3.6 adds no
harness-only behavior and removes some.

Five changes: a comment-only fix doesn't void every stamp; the harness
stops refusing command shapes when the git pre-commit layer is armed;
git-guard drops the checks no agent was seen needing; a review run before
`git add` counts; `status` names hook wiring an installed repo is missing.
The quick fixes from the same audit ship as 3.3.2, not here.

## Evidence

All checked 2026-10-30 against this branch (`7d2a6a2`), prizma and Hatedate
read-only, and the Claude Code transcripts under `~/.claude/projects` (142
project folders).

**1. Any blob change voids every reviewer's stamp on the file.**
- `judge()` owes a file to each routed reviewer whose stamp key isn't the
  staged key (`review-gate.mjs:249`). The key is the blob pair
  (`stagedChanges`, `:121-129`), so a comment edit is a new key.
- The re-review gets the delta (`deltaFor`, `:270`), but every routed
  reviewer still re-runs.
- prizma plan 35 task 3 was "comment/prose only" and ran five rounds
  (`prizma/.ssdd/ledgers/35-last-published-at-writer-ledger.md:16`).
- **The same ledger line cuts the other way.** Those rounds found real
  wrong claims: resilience found two more instances of the class, a round-3
  fix "carried a wrong premise" that resilience's next round caught, and
  bias-semantics and the task reviewer each found one. None came from
  docs-sync, whose contract is doc couplings, not whether a comment is true
  (`reviewers/docs-sync-reviewer.md:12-41`).
- Repeats cost in general: in Hatedate, 31% of 391 reviewer runs were
  repeats (`docs/specs/v3.md:1045-1046`). That was its whole-diff-stamp era,
  so it isn't a comment-only count.
- Routed *docs* barely exist: a doc file owes only the reviewers routed to
  it. prizma's docs-sync route is `^src/`, `^scripts/`, `^supabase/`,
  `package.json`, `.github/workflows/`, with no `docs/`; it does cover every
  source file, as do convention and performance on `.ts`. The friction is
  comment edits in routed source.

**2. The harness refuses shapes the armed pre-commit already judges.**
- In harness mode the gate walks `cd` / `-C` / `pushd` to find the target
  repo (`walk`, `review-gate.mjs:548-580`), denies a call that commits to two
  repos (`:586`), refuses staging chained before a commit unless every path
  is a visible, unrouted `git add` (`BESIDE_ADD`, `chainedAddReason`,
  `:620-693`), and refuses `commit -a/-i/-o` and `commit <pathspec>`
  (`:694-729`). The reason in each message: the hook runs before the
  command, so it reads the index as it was.
- The pre-commit layer judges the index git is committing (`:466-469`). SSDD's
  pre-commit runs it (`mechanisms/hooks/pre-commit:22`); `install` and
  `update` arm it when they can (`armHook`, `bin/ssdd.mjs:347-354`).
- Probed in a scratch repo on git 2.54.0, with a pre-commit that prints
  `git diff --staged --name-only`: `commit -am` showed both modified files,
  `git add c.txt && git commit` showed `c.txt`, and `commit -m z b.txt`
  showed `b.txt`. `GIT_INDEX_FILE` was set in all three.
- The cost: Hatedate's transcripts hold 209 calls that chain staging with a
  commit, and 78 of them add a routed file, so each is refused today
  (`docs/specs/v3.md:1193-1199`). Before v3 Part 3's unrouted exception, 12
  of Hatedate's 14 blocks were docs-only commits or scratch repos
  (`v3.md:1049-1051`).
- prizma arms its pre-commit (`core.hooksPath` set; its
  `.githooks/pre-commit:25` runs `--pre-commit`). Hatedate's is set, but
  see Open 1.

**3. git-guard checks shapes no agent was seen using.**
- A PreToolUse `Edit|Write|MultiEdit|NotebookEdit` entry
  (`adapters/claude-code/settings-hooks.json:41-49`) runs git-guard on every
  file edit in every session, to deny the file tools on `.git/ssdd-review-*`
  (`git-guard.mjs:58-64`). It fires in both stamping modes.
  - Across the 142 transcript folders: no Edit/Write/MultiEdit/NotebookEdit
    call on a `review-stamp` or `review-dispatch` path (the one hit is
    SSDD's own `review-stamp.test.mjs`), and the deny message never
    appears. The four
    self-stamps v3.4's draft found were all `--stamp` calls
    (`git show 68a02e9:docs/specs/v3.4.md`, lines 119-153).
- `core.hooksPath` detection goes past the plain forms: the
  `GIT_CONFIG_PARAMETERS` / `GIT_CONFIG_KEY_<n>` env forms (`viaEnv`,
  `git-guard.mjs:112`), abbreviated write options such as `--unset-a`
  (`isWriteOption`, `:87-89`), and anything the shell expands before the key
  (`configWrites`, `:93-105`).
  - The env forms appear in no prizma or Hatedate transcript; the only
    commands naming them are SSDD sessions searching for them, this one
    included. Hatedate's own hooks never had them (`git log --all
    -G'GIT_CONFIG'` is empty there); they arrived in SSDD's v2.1 scope
    (`docs/specs/v2.1.md:55-56`).
  - The abbreviation and expansion rules came "From the second automated
    review" (`35dbb04`), not from an incident.
- The rule they fail: "A new evasion shape is out of scope unless an agent
  was seen using it in a real project" (`docs/BACKLOG.md`, Threat model;
  `docs/specs/v2.6.md` Clarify 3).

**4. A review run before `git add` counts for nothing, on any harness.**
- `--stamp` refuses a file that isn't staged ("not staged, or not routed",
  `review-gate.mjs:405-410`; `:417` when none is).
- Every reviewer's default input is `git diff --staged`
  (`reviewers/*.md`, "How to run" step 1, e.g.
  `docs-sync-reviewer.md:34`), so a review before `git add` sees nothing.
- Claude Code's completion stamps have the same gap. SubagentStart
  snapshots the reviewer's routed *staged* files only (`:822-826`), and its
  stop stamps nothing for a file staged afterwards (`:853-854`).
- A reviewer that ends without a verdict line is a recorded refusal
  (`:847`), shown only in the next block message. The hook exits 0 whatever
  happens (`:495`, "observational: never blocks a subagent"), and its
  stderr reaches no one: "the orchestrating agent never sees this hook's
  stderr" (`:833-834`).
- `NO DIFF` and a missing verdict both parse to null (`parseVerdict`,
  `:761`), so the hook can't tell an empty input from a forgotten verdict.
- **Claude Code's hooks reference** (code.claude.com/docs/en/hooks, read
  2026-10-30). Recorded because the audit asked; Decision 4 doesn't use it,
  since a SubagentStop block is a Claude-only rule:
  - SubagentStop takes `decision: "block"` with a `reason`: it "keeps the
    subagent running and delivers `reason` to the subagent as its next
    instruction"; exit 2 delivers stderr the same way.
  - Its input carries `stop_hook_active`, "`true` when Claude Code is
    already continuing as a result of a stop hook" (the Stop section); the
    loop protections include an 8-consecutive-continuation cap.
  - SubagentStart "can't block subagent creation"; its `additionalContext`
    goes to the subagent, before its first prompt.

**5. A new hook event in a template never reaches an installed repo, and
nothing says so.**
- `.claude/settings.json` is seeded, so project-owned: `update` "never
  touches them and prints how their templates changed instead"
  (`bin/ssdd.mjs:31-33`; `seedOne` returns when the file exists, `:295-298`;
  the printed diff, `:569-579`). `install` leaves the merge to the user
  (`:368`).
- prizma's and Hatedate's `.claude/settings.json` wire only `PreToolUse`
  and `PostToolUse`: no `SessionStart` (v3 Part 1's session-start check), no
  `SubagentStart` / `SubagentStop` (completion stamps, v3.4's finding parse,
  Decision 4). Both are pre-migration, so this shows what `update` would
  leave, not a regression today.
- v2.6 already leaned on the printed diff to deliver one changed line
  (`docs/specs/v2.6.md`, Scope: the `if` filter).
- Cursor's wiring is different: `.cursor/hooks.json` is a managed file
  (`bin/ssdd.mjs:225`), three-way merged by `update` like the hooks
  themselves. The gap is Claude Code's seeded settings only.
- `status` already warns about a broken config and a dormant pre-commit
  (`gateWarnings`, `bin/ssdd.mjs:700-714`), and changes nothing.

## Decisions

1. **A comment-only change carries a clean stamp forward.**
   - When reviewer R's stamped blob and the staged blob of file F differ
     only in comments, R's stamp still meets the gate, provided:
     - the HEAD side and both modes are unchanged (the key's
       `srcMode:srcBlob` and `dstMode` match), and the stamped blob still
       exists (`deltaFor`'s `'gone'` case doesn't carry);
     - R's stamp records no open issues (`issues` absent or 0; with v3.4,
       no open finding of R's on F). A reviewer that flagged something on
       F re-reviews F: it's the one who can say it's fixed.
     - R isn't the comment reviewer.
   - The comment reviewer, `reviewGate.commentReviewer` (default
     `docs-sync-reviewer`), still owes F and gets the delta as today. When
     it isn't routed to F, nothing carries.
   - It's computed in `judge()`, stateless: the stamp stays on its old key,
     and each judgment compares the stripped blobs again. Nothing new is
     written, so `--check` and `--pre-commit` stay read-only. The triage
     note says which stamps carried.
   - **Comment-only** means the two blobs are byte-equal after stripping
     comments, trailing whitespace and blank lines. Conservative:
     - Only the JS/TS family is classified in v3.6 (`.js .mjs .cjs .jsx .ts
       .tsx .mts .cts`). Any other extension is never comment-only.
     - Strings, template literals and regex literals are tokenized before
       comments. Anything the scanner can't classify (a `/` it can't call
       division or regex, an unterminated token) makes the change code.
     - A comment a tool reads is code: shebang, `eslint-`, `@ts-`,
       `prettier-ignore`, `c8` / `istanbul ignore`, `/*#__PURE__*/`,
       `/// <reference`, `//# sourceMappingURL`, and JSDoc type tags in a
       `.js`-family file. The exact list is a clarify item.
   - docs-sync's contract gains a section: on a comment-only delta, check
     each changed comment's claim against the code it describes. That's the
     class plan 35's rounds caught (Evidence 1).
2. **When the pre-commit is armed, the harness gate steps aside.**
   - The harness still resolves each commit's target repo (`walk`). When
     every target resolves, and each has no config or has a pre-commit that
     runs (`dormantHook(root) === ''` on a repo with `.githooks/pre-commit`),
     the harness allows the call without judging it. The pre-commit judges
     the index git really commits, so staging, stamping and committing can
     share one call.
   - It doesn't judge a bare commit either. Judging the index before a
     chained `git add` would false-block the flow Decision 4 enables
     (review the work tree, then `git add && git commit`), and telling a
     bare commit from a chained one is the parse this decision removes.
   - This moves the rule out of the harness and into git, where every
     harness (and a human) already meets it.
   - Anything else keeps today's behavior: a dormant pre-commit, a target
     it can't read (`$VAR`, `$(…)`, `cd -`, `pushd`), a repo with a config
     and no `.githooks/pre-commit`. The fail-closed target rule stays for
     the reason v2.6 kept it (Clarify 6): the gate can't tell whether that
     repo is armed.
   - Cursor's `beforeShellExecution` uses the same code path, and git runs
     the pre-commit there too, so the rule is harness-neutral.
   - git-guard's `-n` / `--no-verify` block stays: it's what keeps the
     pre-commit in the loop.
3. **git-guard keeps the plain `core.hooksPath` blocks and drops the rest.**
   - The `Edit|Write|MultiEdit|NotebookEdit` entry leaves
     `settings-hooks.json`, and git-guard's file-path check
     (`git-guard.mjs:60-64`) goes. In hooks mode the Bash-side check on
     `--stamp` and `.git/ssdd-review-*` (`:120-126`) stays.
   - Kept: `git -c core.hooksPath=…`, and `git config` naming the key with
     a value after it, or with a write subcommand or option spelled out
     (`set`, `unset`, `--unset`, `--unset-all`, `--add`, `--replace-all`,
     `--edit`). Reads pass, as since v3 Part 3.
   - Dropped: the env forms, abbreviated options, and the shell-expansion
     rule. Each returns with the incident that shows an agent using it.
   - Combined with Decision 2, `GIT_CONFIG_PARAMETERS=… git commit` turns
     off the pre-commit and passes the harness. No agent has written it;
     it's the kind of evasion the threat model leaves to the pre-commit.
     Recorded in `docs/limitations.md`.
4. **A review run before `git add` counts.** One rule, in the gate, for
   every harness.
   - A stamp may name a routed file's work-tree content. An unstaged or
     untracked (not ignored) file is keyed as `git add` would key it:
     `srcMode:srcBlob` from `git ls-tree HEAD`, `dstMode:dstBlob` from its
     file mode and `git hash-object --path`. A later `git add` of the same
     content stages the same key, so the stamp holds.
   - `--stamp` accepts such a file instead of refusing it. Its refusal
     stays for a file that's neither changed nor routed.
   - The reviewer contracts' input becomes `git diff HEAD` (staged and
     unstaged) for the routed files, or the range the orchestrator names.
     Untracked files are named by the orchestrator, as today.
   - Claude Code's completion stamps use the same key function:
     SubagentStart snapshots the reviewer's changed routed files, staged or
     not, and SubagentStop stamps the keys still current. No new hook
     event and no block: a stop with no verdict stays a recorded refusal.
   - A completion stamp that started with nothing routed to it changed
     records a refusal ("nothing routed to it had changed when it
     started"), so the next block message shows it instead of a silent
     "stamped 0 file(s)".
   - `parseVerdict` returns `NO DIFF` as its own result, so the refusal
     says which one happened.
5. **`status` names missing hook wiring; nothing rewrites a project-owned
   file.**
   - For each installed adapter whose wiring is seeded (today Claude Code's
     `.claude/settings.json`), `status` and the end of `update` list the
     template's hook entries the project lacks, as (event, matcher,
     command), with what each one runs. Example: `SubagentStop →
     review-gate.mjs (completion stamps)`.
   - It lists entries the project has that the template dropped, such as
     Decision 3's `Edit|Write` entry, as safe to remove.
   - It's a warning beside `gateWarnings`' others; the project merges, as
     it does today. A file that isn't valid JSON gets one line saying so.
   - Nothing in the gate depends on a hook event being wired: a missing
     one costs only the convenience it adds.

**Interactions with v3.4** (unbuilt; v3.6 doesn't depend on it):
- A carried stamp isn't a review, so it doesn't count as a v3.4 round, and
  it keeps R's findings. Since a stamp with open findings doesn't carry
  (Decision 1), a comment fix to R's own finding still goes back to R, whose
  `✅ [<id>] fixed` closes it (v3.4 Decision 3). docs-sync's re-review
  doesn't close another reviewer's finding.
- Decision 4's work-tree stamps carry v3.4's review ID like any other.
- v3.4 parses findings at SubagentStop, a Claude-only hook. Under v3.6's
  rule its harness-neutral path, `--stamp --report <file>` (v3.4 Decision
  2), is the primary one, and SubagentStop the Claude convenience. That's
  for v3.4's clarify pass to adopt; v3.6 doesn't change v3.4.

## Scope

**In:**
- review-gate: the comment-only carry in `judge()` and the triage note;
  the step-aside rule in harness mode; work-tree keys in `--stamp` and in
  the completion-stamp snapshot; the empty-snapshot refusal; `NO DIFF` as
  a result.
- The five framework reviewers and the domain template: the input line
  reads `git diff HEAD` for the routed files. 3.3.2 rewrites their report blocks and
  gives docs-sync the key inventory (branch
  `claude/3-3-2-process-text-e5f22e`, `eca0a4f`), so v3.6's reviewer edits
  start from that text.
- A comment stripper for the JS/TS family, no dependencies, in
  `mechanisms/hooks/`.
- git-guard: the file-path check and the env / abbreviation / expansion
  rules removed; header comment updated.
- `adapters/claude-code/settings-hooks.json`: the `Edit|Write…` git-guard
  entry removed.
- `bin/ssdd.mjs`: the missing-wiring warning in `status` and at the end of
  `update`.
- `reviewers/docs-sync-reviewer.md`: the comment-claim section.
- Config: `reviewGate.commentReviewer`.
- `docs/limitations.md`, README's threat-model lines, `SDD.md` §4 (one call
  can stage, stamp and commit when the pre-commit is armed), the selftests
  (`review-gate.shapes.selftest.mjs` keeps its cases for a dormant repo),
  and CHANGELOG.

**Out:**
- Comment-only for other languages (Python, SQL, shell). Each needs its
  own scanner and the same "unsure is code" rule. Add one when a project's
  ledgers show the rounds.
- Prose-only changes in a routed doc: its reviewers are routed to the prose
  on purpose.
- Removing the shape checks for a dormant repo (Open 1).
- Any rule only one harness can run: a SubagentStop block on a missing
  verdict, SubagentStart `additionalContext`, an installer that edits a
  harness's settings.
- Blocking a commit on anything new.
- The 3.3.2 quick fixes from the same audit.

**Footprint:** one scanner and one comparison in `judge()`, one harness
early exit, one key function shared by `--stamp` and the completion stamps,
one warning in `status`, and one config key. It deletes a hook entry and
about 30 lines of git-guard. No new hook event, no new git hook, no new
block, nothing only one harness runs.

## Open

1. **Decision 2, the owner check: was the pre-commit armed when the
   chained-add rule answered its incident?** It didn't matter: the
   pre-commit never ran the review gate there.
   - The incident is Hatedate's "2026-08-10 wip-commit incident": "a
     chained 'git add ... && git commit' with a clean index passed the
     empty-staged early-exit and committed un-reviewed" (Hatedate
     `50207a0b`, 2026-08-10). v2.1 ported the fix (`v2.1.md:16-23`), and
     v2.6 kept it as real (`v2.6.md` Clarify 1).
   - Hatedate's gate then was `.claude/hooks/review-gate.mjs`, a
     "PreToolUse(Bash) review gate" with no pre-commit mode. Its
     `.githooks/pre-commit` (163 lines at `50207a0b`) checks untracked
     files and asset imports, and mentions no review gate. It still doesn't
     today (`git log -S'review-gate' -- .githooks/pre-commit` is empty).
   - Whether `core.hooksPath` was set that day isn't recorded (it's local
     config), and it doesn't change the answer.
   - So the rule answered a gate with one layer. SSDD's armed pre-commit
     judges the committed index (Evidence 2), which closes that incident's
     shape on its own. My call: step aside as Decision 2 says.
   - Also for the owner: by your rule (hard blocks only where irreversible
     or outward-facing), should the shape checks go for a *dormant* repo
     too, replaced by the dormant-hook warning the gate already prints
     (`review-gate.mjs:737-742`)? A local commit can be undone; the push is
     what goes out. My call: keep them for dormant repos in v3.6, since a
     dormant repo has no other layer, and revisit after the migrations arm
     both projects.
2. **Decision 1's evidence is mixed.** Plan 35's comment-only rounds were
   costly, and they also caught wrong claims, through resilience,
   bias-semantics and the task reviewer. Clean stamps carrying plus
   docs-sync checking comment claims recovers some of that, not all: a
   reviewer that was clean on F before won't see a new wrong comment on F.
   Options: (a) as decided; (b) carry only for whitespace and comment
   deletions; (c) drop Decision 1. My call: (a).
3. **Sequencing.** The migrations wait for v3.4 (owner, 2026-10-22).
   Nothing in v3.6 has to come first: no rule depends on a hook event. It
   lowers costs the migrated projects will pay, so it's worth having, not
   worth waiting for. My call: after v3.4; ship it before the migrations if
   it's ready, and don't hold them for it.

## Clarify pass

*Not run.* It has to settle at least:
- The JS/TS scanner's grammar: regex-versus-division, JSX text, nested
  template literals, and the list of tool-read comments. Test it on prizma's
  and SSDD's own history: every comment-only commit it finds, and no code
  change it calls comment-only.
- Whether "byte-equal after stripping" should also ignore a line that only
  moves, so reflowing a comment block doesn't shift code lines.
- Decision 2: what the pre-commit's block message loses (the harness adds
  `--repo` for a commit to another work tree, `:597-600`, and the triage
  note as `additionalContext`), and whether it matters.
- Decision 2: what "armed" checks. `dormantHook` only asks whether a
  pre-commit exists where `core.hooksPath` points (`ssdd-config.mjs:190-212`),
  and Hatedate is the counterexample: set, present, and never running the
  gate. If adoption sidecars Hatedate's pre-commit instead of replacing it,
  the harness would step aside with nothing behind it. "Armed" has to mean
  that pre-commit is SSDD's: its hash matches the lock's managed entry, or
  it runs `review-gate.mjs --pre-commit`. Otherwise the repo counts as
  dormant.
- Decision 2 with a linked worktree whose `core.hooksPath` is the main
  checkout's absolute path (`foreignHook`, `ssdd-config.mjs:214-222`): it
  runs, so it counts as armed.
- Decision 4: a file both staged and edited after staging has two keys.
  Which one a stamp names (a manual `--stamp`, and the snapshot) needs a
  rule; `git diff HEAD` shows the reviewer the work-tree one.
- Decision 4: `git hash-object --path` applies the same clean filters as
  `git add` (autocrlf, LFS); check on a repo that uses them.
- Decision 5: what counts as the same entry when a project wrapped the
  command (a different path, extra env).
- Codex and other harnesses with no adapter: confirm they meet only the
  pre-commit and the CLI, and that Decisions 1, 2 and 4 behave the same
  there.
- Version: 3.6.0 (MINOR). The config key is additive; no project-owned
  file changes.
