# v3.5 — findings have outcomes

**Date:** 2026-10-22, trimmed 2026-10-23, revised for v3.4 2026-10-30 · **Status:** clarified 2026-10-30 · **Branch:** `claude/v3-4-plan-98c5d4` (plan: `docs/superpowers/plans/2026-10-30-v3-5-findings.md`)

## Goal

The gate loop converges. A re-review is told which findings are still open,
answers each one by ID, and never repeats one; a finding the change didn't
introduce doesn't hold the commit; a loop that keeps going says so. Today the
gate proves that a reviewer ran and keeps a count; it doesn't know what the
reviewer found, so the next round can't build on it.

**Trimmed** (owner, 2026-10-23): the first draft also blocked commits on open
findings, recorded every outcome in the commit message, and standardized
`BACKLOG.md`. The first two are deferred (Out); the third is its own spec,
`SPEC.md` → v3.6. The full draft, with its evidence for the deferred parts,
is `git show 68a02e9:docs/specs/v3.4.md`.

**Revised for v3.4** (owner, 2026-10-30): v3.4 (`SPEC.md` → v3.4) makes the
git pre-commit the only review gate and `--stamp` the only way to stamp,
and removes Claude Code's completion stamps, so SSDD works the same on any
harness. This draft read findings at SubagentStop; it now reads them from
the report `--stamp` is given. v3.5 is built on v3.4. The draft before this

## Decisions

1. **One outcome vocabulary.** `fixed`, `wrong` (a false positive),
   `intentional` (by design), `minor` (true, not worth the change),
   `deferred` (real; it gets a home, as `SDD.md` §3 already requires) and
   `pre-existing`. Each carries a one-line reason. The ledger's triage, the
   triage note and the reviewer contract use these words.
   - The gate sets two of them: `fixed` from a re-review (Decision 3) and
     `pre-existing` from the reviewer's tag (Decision 4).
   - The rest are the author's triage, written in the ledger or the commit
     message, as today (`SDD.md` §4 step 3). Nothing checks them; that's
     deferred (Out).
2. **Findings are parsed from the report `--stamp` is given, and belong to
   the review.**
   - `--stamp <reviewer> --report <file>` reads the reviewer's final text
     from the file (`-` for stdin). It parses the verdict line and each `❌`
     and `⚠️` line into an ID, reviewer, kind, cited `path:line` and text.
     The orchestrator saves each reviewer's reply as it comes back; that's
     the only new step, and it's the same on every harness.
   - A report with no verdict line is refused with the reason, so the
     orchestrator can re-ask the reviewer; nothing is stamped.
   - A review is one reviewer plus the files it stamped; each stamp entry
     gains the ID of the review that wrote it. A finding can cite a file
     outside that set (resilience traces a retry owner to another file).
   - The findings sit in the stamp file next to the stamps. They're work
     state, not a record, and go stale with the stamps they belong to.
   - `--report` is optional (Open 1). A `--stamp` without it stamps as
     today, records no findings, and prints one line: the next re-review of
     those files gets the delta only, not the open findings.
   - The triage note names each open `❌` by ID on the file it cites,
     instead of copying a count onto every file. It still doesn't block.
     `--check` lists the open `❌` too.
3. **The re-review is told what's open, and says what it fixed.**
   - For a file a reviewer stamped with open findings, the block message
     gives the delta (as today), plus those findings by ID and text.
   - The reviewer contract gains one line: for each listed finding,
     `✅ [<id>] fixed` or `❌ [<id>]` (still open); never re-report one
     that's listed.
   - Only `✅ [<id>] fixed` records `fixed`. Silence leaves the finding
     open: a stamp covers every routed file the reviewer owns unless
     `--files` narrows it, whatever its input named (`SDD.md` §4 step 3), so
     silence-means-fixed would close findings on files the re-review never
     read.
   - This is the article's auto-clear and no-repeat rule, held to the
     refute-by-default standard of `SDD.md:121`.
4. **Pre-existing is a test, not a location:** the finding holds against
   HEAD's version of the code. A caller the change breaks sits on an
   untouched line and isn't pre-existing.
   - The reviewer writes `❌ [pre-existing] …`; it's recorded as
     `pre-existing`, isn't listed as open, and doesn't count toward a round.
   - A `[pre-existing]` finding that cites a line the change adds loses the
     tag. The added lines come from convention-lint's `addedLines`
     (`convention-lint.mjs:100`).
   - Moved code is the author's call: triage it `pre-existing` with the
     reason. An author who fixes one anyway gets `✅ [<id>] fixed` from the
     next review like any other.
5. **A round cap on the gate loop that warns.** It applies to the gate's
   per-file rounds, the loop that ran to 12 in prizma, not to Superpowers'
   task fix loop.
   - A round is a review by reviewer R of file F where R's previous stamp on
     F had open findings and the same HEAD-side blob. A commit or a rebase
     starts the count over.
   - At `reviewGate.maxRounds` (default 3) the block message says not to
     dispatch another round: list the open findings and ask the user whether
     to rethink the approach or triage them.
   - It's a warning, like `maxRoutedFiles` (`review-gate.mjs:285-296`), not
     a block.

## Scope

**In:**
- review-gate: the finding parse in `--stamp --report`, findings in the
  stamp file, the re-review list in the block message, the triage note and
  `--check` naming open findings by ID,
  the round count and its warning, the `[pre-existing]` added-line check.
- The five framework reviewers and the domain template: the
  `[pre-existing]` tag, `✅/❌ [<id>]` answers, no repeats.
- `SDD.md` §3 and §4 step 3, and the ledger template's triage line: the
  outcome words.
- Config: `reviewGate.maxRounds`.
- The selftests and CHANGELOG.

**Out (deferred, from the first draft):**
- **Blocking a commit on an open `❌`, with the author proposing an outcome
  and the reviewer or the user ruling** (draft Decisions 4–5:
  `--propose`, `--rule`, `--report` required in block mode).
  - It costs a step per finding and possibly a dispatch, and a proposal no
    re-review picked up would stay pending until `/cleanup`, which SSDD
    doesn't require before merge.
  - The evidence points the other way: prizma left findings unfixed "rather
    than void the file's stamps" (39:59), and silent drops had no evidence
    either way.
  - Revisit if the triage note and the parsed findings show `❌` committed
    with no triage.
- **The commit message as the record** (draft Decisions 9–11: `SSDD-`
  lines, a `commit-msg` hook, `--findings`, `/cleanup --checked`).
  - It's a second system: a new git hook, a line per unfixed finding in
    every routed commit, a public-repo switch, and about twenty open
    mechanism questions (IDs across rounds, squash, amend, the line
    grammar).
  - The smallest version, if the noise metric is wanted later, is one
    counts-only `SSDD-Review:` line.
- **A standard `BACKLOG.md` and `/migrate-backlog`:** `SPEC.md` → v3.6.
- Severity tags across all reviewers (only security rates severity today).
- A verifier agent per finding: declined in v3 Part 5 (`v3.md:2454`), and
  prizma's one majority vote dropped none of 47 findings.
- Past incident PRs as a test set; nightly sweeps of old code; the
  article's risk tiers, required approvals and merge queue.

**Footprint:** one optional flag on `--stamp` and its parse, findings in
the stamp file the gate already keeps, a few lines per reviewer, and one
config key. No new git hook, no harness hook at all, no new script, nothing
that blocks a commit. It runs the same in Claude Code, Cursor and a
terminal.

## Clarify pass

Sources: the code at `3cf89af` (3.3.2, the reviewers' rewritten report
blocks included), `docs/specs/v3.6.md` at `3ee431a` (now v3.4), and the reviewer
replies in the Claude Code transcripts of prizma and Hatedate (read-only:
3,557 subagent transcripts under `~/.claude/projects`, of which 2,189 end
with a verdict line). All checked 2026-10-30. No item needed the owner;
each is my call, recorded here so the owner can overrule it. What v3.5
assumes of v3.4, which isn't built yet, is listed once, in the plan's
"Built on v3.4" section.

1. **Real reports, measured.**
   - Of the 2,189 replies, with markup dropped, the lines that start with
     `❌` number exactly N in 1,687 (77%), the `❌` and `⚠️` lines together
     in 259 (12%), and neither in 243 (11%). 90 say N > 0 and have no `❌`
     or `⚠️` line: their findings are numbered headings.
   - Of 1,390 `❌` lines, 773 (56%) cite `path:line` on the line itself,
     445 with an absolute path. The rest put the path on a following line
     or cite none: docs-sync's form ends in `<doc + section>`
     (`reviewers/docs-sync-reviewer.md:43`).
   - So the contract tightens the format (item 3), and the parse is
     tolerant and never refuses for a count (item 4).
2. **The finding-line grammar.**
   - A line is a finding when, after its leading markup is dropped
     (whitespace, `>`, `#`, `|`, a list marker `-` `*` `+`, a number `1.` or
     `1)`, `**`, `_`, backticks), it starts with `❌` or `⚠️` (`⚠` with or
     without U+FE0F). A line whose mark comes later ("0 ❌, 4 ⚠️") isn't
     one, and neither is a verdict line.
   - After the mark, an optional bracket: `[pre-existing]` or `[F<n>]`.
     Security's severity word is part of the text:
     `❌ [pre-existing] Critical …`.
   - The cited place is the first `path:line` or `path:line-line` on the
     finding's line, else on the lines after it up to the next finding,
     `✅` line, heading or blank line, else none. Backticks and bold around
     it are dropped; an absolute path under the repo root becomes
     repo-relative.
   - The text kept is the finding's line, markup dropped, at most 300
     characters.
   - Answers: `✅ [F<n>]` (whatever follows) records `fixed`; `❌ [F<n>] …`
     keeps F<n> open and counts as a `❌`. Neither makes a new finding.
   - The verdict is read as `parseVerdict` read it before v3.4 removes it
     (`review-gate.mjs:759`): the last three non-empty lines, `CLEAN` /
     `SECURE` / `N ISSUE(S)` / `N RISK(S)`. `NO DIFF`, or no verdict,
     refuses the stamp.
3. **The contract line.** Each reviewer's "How to run" gains a step after
   its report step:
   > One finding per line, starting with `❌` or `⚠️` and citing
   > `path:line` (repo-relative) on that line. A finding that holds against
   > HEAD's code too is `❌ [pre-existing] …`. Given open findings, answer
   > each on its own line, `✅ [<id>] fixed` or `❌ [<id>] <why it's still
   > open>`, and never report a listed one again. N counts the `❌` lines.
   - docs-sync cites its doc as `path` or `path:line`.
   - **Six reviewers, not five.** `gate-reviewer.md` has the same report
     block (`:37-40`), and its check 5 names the verdict line the stamp
     parses (`:67-69`). It gets the step, and check 5 adds the finding
     grammar as a gate surface. So do the domain template and, through it,
     `/new-reviewer`. Scope's "five framework reviewers" is read as all of
     them.
4. **A count that doesn't match N.** The stamp lands, the findings parsed
   are recorded, and `--stamp` prints one line with both counts, saying the
   re-review will list only the parsed ones. Refusing would hold a commit
   on a format slip, against the owner's rule (Open 1's reasoning); 23% of
   the sample would have been refused. Only a missing verdict refuses
   (Decision 2).
5. **`⚠️` is recorded, never open.** Open means a `❌` with no outcome.
   `⚠️` doesn't make a review a round and isn't in the triage note, so a
   review of judgment calls alone starts no loop. The re-review sees it
   under "already noted", so it isn't reported again.
6. **IDs.**
   - A finding is `F<n>`, a review `r<n>`, both from one counter in the
     stamp file (`next`), never reused while the file exists. Short enough
     to echo in `✅ [F12] fixed`, and not derived from the text or the
     line: the re-review matches a finding to the code by reading its text
     (Decision 3), so a moved or reworded finding keeps its ID. A hash of
     reviewer and text would be longer and change with a reword.
   - A new `❌` whose text, markup dropped and case folded, equals an open
     finding of the same reviewer is that finding, still open. The
     contract says never repeat one; this holds it when a reviewer slips.
7. **The stamp file stays version 2.**
   - Its new fields are additive, as v2.3's were: `readStamp` checks only
     `version === 2` and `reviewers` (`review-gate.mjs:177-185`), and
     `updateStamp` writes back the whole parsed object (`:191-206`), so a
     gate from before v3.5 keeps the new keys.
   - The shape:
     ```
     { "version": 2,
       "reviewers": { "<name>": { "<path>": { "key", "at", "review": "r7", "round": 2 } } },
       "reviews": { "r7": { "reviewer", "at", "verdict", "issues",
                            "files": { "<path>": "<key>" },
                            "findings": { "F8": { "kind": "❌", "path", "line", "text", "outcome", "by" } } } },
       "next": 9 }
     ```
   - Only the gate sets `outcome`: `fixed` (with `by`, the review that said
     so) or `pre-existing`. The author's triage stays in the ledger
     (Decision 1). A stamp without `--report` writes no `review` and no
     `reviews` entry.
   - **A review is current** while one of its files is still in the change
     with the HEAD side its key recorded. Only a current review's findings
     are listed, counted or named. A commit or a rebase moves the HEAD
     side, so its review goes stale with its stamps (Decision 2).
     `--stamp` drops stale reviews when it writes; `--check` and
     `--pre-commit` stay read-only.
   - **A file deleted or renamed between rounds:** `--no-renames` makes a
     rename a deletion and an addition (`review-gate.mjs:124-132`). A
     finding keeps the path it cited and is listed as written while its
     review is current; the re-review answers it by its text.
8. **Rounds.**
   - `round` lives on `reviewers[R][F]`. A stamp of R on F sets it to the
     previous entry's `round` + 1 when that entry has the same HEAD side
     and R had an open `❌` in a current review when the stamp began;
     otherwise to 1. A stamp without `--report` counts too: it's a review
     either way. A stamp v3.4 carries isn't written, so it isn't a round.
   - "Open findings" here is per reviewer, not per file: a finding belongs
     to the review and may cite another file (resilience's retry owner),
     so a fix that lands in another file still counts as the next round.
   - At `round` ≥ `reviewGate.maxRounds` on a file R owes, with an open
     `❌` of R's, the block message warns under R. `maxRounds` is read as
     `maxRoutedFiles` is (`review-gate.mjs:285-296`): a positive integer,
     else 3; `ssdd-config.mjs` doesn't validate it.
9. **What the re-review is told, and the triage note.**
   - Under each owing reviewer R, the block message lists R's open `❌`
     from its current reviews, by ID, cited place and text, whatever file
     each cites, then R's `⚠️` as already noted.
   - `--check` prints the same message, so that list is the form to paste
     into the dispatch; there's no second format. The orchestrator passes
     it on with the delta (`SDD.md` §4 step 2).
   - The triage note (nothing owed: `--pre-commit` and `--check`) lists
     each open `❌` of a current review as `[F<n>] <reviewer> — <place> —
     <text>`, and drops today's per-file count (`review-gate.mjs:212-228`).
10. **`--report` and several reviewers.** `--report` goes with exactly one
    reviewer: `--stamp a,b --report x` is refused with the usage line, and
    nothing is written. The block message prints one stamp line per owing
    reviewer, each with `--report <its reply>`. `--stamp a,b` without
    `--report` still works and prints the one-line note.
11. **Where reports live.** `--report <file>`, or `-` for stdin. The gate
    copies what it parsed into the stamp file and neither keeps nor deletes
    the file. `SDD.md` tells the orchestrator to save each reply outside
    the work tree (a temp dir) or pipe it with `-`. Not inside `.git`, as
    this item first proposed: in a linked worktree `.git` is a file (this
    branch's is), so the agent would need `git rev-parse --git-path` to
    find the directory, and nothing would ever clean it. Inside the work
    tree a report would be an untracked file.
12. **`[pre-existing]` and the added lines.**
    - `addedLines` and `diffPath` move from `convention-lint.mjs`
      (`:103`, `:122`) into a module both import. The lint can't be
      imported: it reads stdin when loaded (`:36-37`).
    - The diff is the stamped change's blob pair, `git diff -U0 <srcBlob>
      <dstBlob>`, not the index: with v3.4's work-tree keys the index may
      not hold what was reviewed. `--stamp` writes the reviewed blob into
      the object store first (`git hash-object -w --path`) when it isn't
      there. A file new in the change has every line added.
    - A cited path in the review's files uses its stamped key; one in the
      change but not the review's files, its current key; one not in the
      change has no added lines.
    - The tag is dropped when the cited line, or any line of a cited
      range, is added. A `[pre-existing]` finding with no line keeps its
      tag unless its file is new. `--stamp` names each dropped tag.
13. **`SDD.md`'s budget.** It's 10,990 of 11,000 bytes
    (`bin/repo.selftest.mjs:180`). v3.5 adds the outcome words (§3), the
    report step (§4 step 3) and the gate's IDs ("Findings are records"),
    about 600 bytes. v3.4 removes §4 step 3's completion-stamp sentences
    and step 4's harness-gate rule, about 900. If that falls short, the
    plan cuts restated text from §4 before any ruling to raise the budget.
14. **Version: 3.5.0, MINOR.** v3.4 ships first as 3.4.0, so this spec's
    name is its version (renumbered 2026-11-01; drafted as 3.7.0). The
    stamp file stays version 2 and
    readable both ways, the config key is optional, and the reviewer files
    are managed and update cleanly: MINOR by the CHANGELOG's rule.

## Acceptance criteria

- **AC1 — The parse.**
  - Each reviewer's documented form parses to kind, place and text,
    security's severity and docs-sync's doc citation included. So do a
    heading, bold, a numbered or bulleted line, a backticked line, an
    absolute path, and a path on the next line.
  - "0 ❌, 4 ⚠️" in prose, and the verdict line, aren't findings.
  - `✅ [F3] fixed` and `❌ [F3] …` are answers; `[pre-existing]` is a tag.
  - `NO DIFF`, no verdict, and an empty input return a reason, no result.
  - **On real data:** the 2,189 sampled replies parse without a throw, and
    the parsed `❌` count equals N in at least the 1,687 the sample
    measured.
- **AC2 — `--stamp --report`.**
  - A report with two `❌` and a `⚠️` stamps the files and records three
    findings with new IDs, which `--stamp` prints. `-` reads stdin.
  - A report with no verdict, with `NO DIFF`, or a file that can't be read
    is refused with its reason, and `--report` with two reviewers is
    refused with the usage line. Each writes nothing.
  - A count that doesn't match N stamps and prints both counts.
  - Without `--report`, the stamp records no findings and prints the
    one-line note.
  - A stale review is gone from the stamp file after the next `--stamp`.
- **AC3 — The re-review list.**
  - After a report with a `❌` on F and an edit to F, the block message
    lists, under R, the delta, the open `❌` by ID, place and text, and the
    `⚠️` as already noted. `--check` prints the same.
  - A report answering `✅ [<id>] fixed` closes it, and it isn't listed
    again. A report that doesn't mention it leaves it open.
  - An answer naming another reviewer's ID is ignored, with a note. A new
    `❌` with an open finding's text keeps that finding's ID.
- **AC4 — `[pre-existing]`.** A tagged `❌` citing an unchanged line is
  recorded `pre-existing`, isn't listed, and doesn't make the next stamp a
  round. One citing an added line, or a line in a new file, is an open
  `❌` and `--stamp` names the dropped tag. One with no line on a changed
  file keeps its tag.
- **AC5 — Rounds.**
  - Three stamps of R on F, each leaving a `❌` open, reach round 3. The
    block message then warns under R, naming `reviewGate.maxRounds`, not to
    dispatch another round: list the open findings and ask the user. With
    `maxRounds: 2` it warns a round earlier.
  - A commit, or a stamp after every `❌` is fixed, starts again at 1.
  - Every exit code is as without the warning.
- **AC6 — The triage note.** Committing with an open `❌` passes, and
  `--pre-commit` names it as `[F<n>] <reviewer> — <place> — <text>`. A
  staged file no finding cites isn't named. `--check` with nothing owed
  prints the same note.
- **AC7 — Compatibility.** A stamp file without `reviews` gates as before.
