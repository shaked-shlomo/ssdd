# v3.5 — one backlog

**Date:** 2026-10-23 (split from the v3.4 draft) · **Status:** clarified 2026-10-30 · **Branch:** none yet · **Plan:** `docs/superpowers/plans/2026-10-30-v3-5-backlog.md`

## Goal

Every SSDD repo keeps its remaining work, deferred review findings included,
in one file with one name: `BACKLOG.md`. A repo that already has such a file
under another name migrates it once, after the user sees what moves.

## Evidence

From the v3.4 draft (`git show 68a02e9:docs/specs/v3.4.md`), checked
2026-10-22:
- **Both projects already keep deferred findings in a committed doc.**
  - prizma's `docs/pre-launch-requirements.md` opens with the rule that
    deferred review findings "get a row the moment they're deferred — a
    finding with no row here doesn't exist". It has 11 "Deferred review
    findings — plan N" sections.
  - Hatedate parks findings in `REQUIREMENTS_BEFORE_PRODUCTION.md` §0 (for
    example, ledger 61:60's "REQUIREMENTS §0 note").
- **The two files differ in name, place and shape.**
  - prizma's is 4,243 lines: Done (about 620), Decisions to review,
    Mandatory before launch, Optional. 193 lines in 92 files name it.
  - Hatedate's is 510 lines, in sections §0–§4 (§4 is completed history).
    349 lines in 147 files name it.
  - Most of those references are plans, ledgers and audits.
- **SSDD has no standard for this doc.** `SDD.md` §7 says to "update the
  requirements/production checklist" without naming one, and the ledger
  template's Follow-ups and `/new-reviewer`'s "requirements checklist" name
  it three more ways. Nothing checks that a deferred finding got its row.
  SSDD's own is `docs/BACKLOG.md`.
- **Deferred items lose their home anyway.** SSDD's own ledgers hold 34
  `minor (deferred)` lines; the 2026-10-23 audit found most of them in none
  of `BACKLOG.md`, `CHANGELOG.md` or a spec, though `SDD.md` §3 says
  "Deferred items get a home before the plan closes" (not re-verified
  line by line).

## Decisions

1. **Every SSDD repo has a `BACKLOG.md`, and deferred findings live in it**
   (owner, 2026-10-22: one standard file, not a path per project).
   - It sits at the repo root, beside `AGENTS.md`. `install` seeds it from a
     template when the repo has none.
   - The template is small: Now, Next, Later, Deferred review findings, and
     Done. A project may add sections of its own.
   - A deferred finding gets one row, one line, carrying its v3.4 finding
     ID when it has one. That's prizma's rule, "a finding with no row here
     doesn't exist", made the standard. It's a process rule; nothing in the
     gate checks it (see Out).
   - On a public repo, a deferred security finding's row is public. It
     names the problem and where it is, never how to exploit it. The
     template says so, and so does the security reviewer's contract.
   - These all become `BACKLOG.md`: `SDD.md` §7's "requirements/production
     checklist", the ledger template's Follow-ups, and `/new-reviewer`'s
     "requirements checklist".
2. **A repo whose backlog has another name migrates it, and is told exactly
   what moves.**
   - `install` and `update` look for a candidate: a file at the root or in
     `docs/` named like a backlog (BACKLOG, TODO, ROADMAP, REQUIREMENTS…,
     …requirements, …checklist). When there is one, they don't seed over
     it. They name it and point to `/migrate-backlog`.
   - `/migrate-backlog` changes nothing until the user approves its report.
     The report lists:
     - the rename: the old path → `BACKLOG.md`
     - how each existing section maps onto the template, and which ones
       stay as they are
     - the rows it moves under Deferred review findings, with a count. They
       keep their words; the row form is for new rows (Clarify 2)
     - every mention of the old file it rewrites, grouped (instructions,
       reviewers, skills, plans, ledgers, audits), with a count per group
   - Afterwards, every mention points to `BACKLOG.md`, history included
     (owner, 2026-10-22): paths and links, section anchors the reformat
     renames, and short names such as Hatedate's "REQUIREMENTS §0".
   - No stub is left at the old path, since nothing in the repo names it
     any more.
   - It lands as one commit on a branch, like `/migrate-plans`.

## Scope

**In:**
- The `BACKLOG.md` template, and a row for it in the AGENTS template's
  Documentation Map.
- The installer seeding it, or naming a candidate file instead.
- `/migrate-backlog`, a new skill (`disable-model-invocation: true`: the
  user runs it once, by name).
- `SDD.md` §3 and §7, the ledger template, `/new-reviewer` and the
  docs-sync reviewer naming it (Clarify 7).
- The security reviewer's line on public rows, and its threat-model
  citation (Clarify 8).
- SSDD's own `docs/BACKLOG.md` moving to the root (Clarify 9).
- The selftests and CHANGELOG.

**Out:**
- **The gate checking that a deferred finding's ID is in the staged
  `BACKLOG.md`.** The v3.4 draft closed a `deferred` finding only then; it
  rode on the propose-and-rule machinery v3.4 deferred, and returns with
  it.

## Open

**Resolved by the owner, 2026-10-30:** both as my call.

1. **Sequencing.** v3.4 ships before the prizma and Hatedate migrations so
   each project migrates once (owner, 2026-10-22). The same reasoning puts
   v3.5 before them too, since `/migrate-backlog` is a per-project
   migration. **Ruling:** v3.5 ships before the migrations. The order is
   v3.6, v3.4, v3.5, then the migrations.
2. **Done history in the migration.** prizma's Done section is about 620
   lines; Hatedate's §4 is its completed history. Keep it in `BACKLOG.md`
   under Done, or move it to a history file? SSDD's own backlog deletes
   shipped items and records them in CHANGELOG. **Ruling:** keep it under
   Done, word for word, and the report says so. SSDD's own backlog keeps
   its rule (delete, record in CHANGELOG); the template allows either.

## Clarify pass

Sources: `bin/ssdd.mjs` (at `9bfacde`, v3.3.2), `process/SDD.md`,
`process/templates/`, `adapters/generic/AGENTS.md`, `reviewers/`,
`skills/new-reviewer` and `skills/migrate-plans`, `bin/*.selftest.mjs`, and
read-only looks at prizma's `docs/pre-launch-requirements.md` (at
`a84124c`) and Hatedate's `REQUIREMENTS_BEFORE_PRODUCTION.md` (at
`0e850543`). All checked 2026-10-30.

1. **Where the template lives, and how it's seeded.**
   - `process/templates/backlog-template.md`, beside the plan and ledger
     templates. `plan()` (`bin/ssdd.mjs:212`) walks `process/` into managed
     files, so it is also installed as
     `.ssdd/process/templates/backlog-template.md`, and `update` keeps that
     copy current. It's also the source of a new seeded entry,
     `BACKLOG.md`, next to `AGENTS.md`'s (`ssdd.mjs:234`).
   - Seeded files are project-owned: `update` never touches one that
     exists and prints how its template changed (`ssdd.mjs:569-579`).
   - `update` also seeds a seeded file that is missing (`ssdd.mjs:570`), so
     a repo installed before 3.5 gets `BACKLOG.md` on its next update. The
     candidate check (Clarify 3) therefore sits in `seedOne`
     (`ssdd.mjs:295`), which both paths call.
   - The seeded file has the five sections and an HTML comment under two
     of them, the AGENTS template's style. No `<placeholder>` text: it's
     usable as seeded.
2. **The row form.**
   - A new deferred finding is one line under `## Deferred review
     findings`:
     `- [<id>] <severity> <the problem> — <path> (<reviewer>, plan NN, YYYY-MM-DD)`.
   - `<id>` is the finding's v3.4 ID. v3.4's clarify pass still sets the ID
     format (its "The ID format" item); v3.5 uses whatever it settles,
     inside `[]` as v3.4's `✅ [<id>] fixed` answers write it. A finding
     with no ID writes `[plan NN]`.
   - When it's fixed, the row moves to Done with the fix commit.
   - Rows that exist before the migration keep their words. prizma's 64
     rows under its 11 "Deferred review findings — plan N" sections are
     paragraphs, some 20 lines long; Hatedate's parked findings are rows
     of §0's roadmap table, by audit ID (`CA37`). Folding them into one
     line would delete text. So the migration moves them under the
     standard heading as they are, and its report counts them as moved:
     11 sections and 64 rows for prizma, none for Hatedate (§0 maps to Now
     whole).
3. **What makes a file a candidate.**
   - A `.md` file at the root or directly in `docs/`, not deeper, whose
     name without `.md` matches, ignoring case:
     `^(backlog|todo|roadmap)$`, or starts with `requirements`, or ends
     with `requirements` or `checklist`. Words may be joined by `-`, `_` or
     a space.
   - Only when the root has no `BACKLOG.md`: an existing one is the
     backlog, and nothing is searched.
   - Measured: prizma has one, `docs/pre-launch-requirements.md`; Hatedate
     has one, `REQUIREMENTS_BEFORE_PRODUCTION.md`; SSDD has one,
     `docs/BACKLOG.md`. None has a false hit, and `requirements.txt` isn't
     `.md`.
   - With one or more, `BACKLOG.md` isn't seeded. The installer prints
     `not seeded BACKLOG.md: <path>[, <path>] looks like this repo's
     backlog — run /migrate-backlog`. With two or more, the skill asks
     which one is the backlog; the others stay where they are.
4. **Finding every mention.**
   - Measured, as `git grep` lines naming the path: prizma 196 lines in 94
     files, 18 of them not markdown (14 under `src/` and `scripts/`, 3 SQL
     migrations, `next.config.ts`); Hatedate 349 lines in 147 files, 9 not
     markdown (6 app files, an edge function, 2 SQL migrations). Every
     non-markdown mention is a comment.
   - Markdown links to the file: prizma 0, Hatedate 4. A link is rewritten
     to the relative path from its own file to `BACKLOG.md`.
   - Section anchors (`<file>#…`): 0 in either repo, and 0 `](#` links
     inside either file.
   - Short names, measured: Hatedate's `REQUIREMENTS §3B` (13), `§1A`
     (11), `§0` (4), `§1B` (2), `§3`, `§2C`, `§2` (1 each) and "the
     requirements file" (2); prizma's "the pre-launch doc", "the pre-launch
     checklist", "the requirements checklist" and "the readiness
     checklist" (12 lines outside SSDD's managed files). A short name has
     no fixed shape, so the skill proposes a list, found by grepping the
     old file's distinctive words (`REQUIREMENTS §`, `pre-launch`,
     `checklist`), with a count and a replacement for each. The user approves each name; none is rewritten
     unasked.
   - Files SSDD manages (the lock's `managed` paths) are skipped. prizma's
     `.ssdd/process/templates/task-ledger-template.md:31` and
     `.ssdd/reviewers/docs-sync-reviewer.md:21` name "the requirements
     checklist"; `update` to 3.5 rewrites those. So the skill needs a lock
     at 3.5.0 or later, and says to run `update` (or `install`) first.
   - Code and migration comments are their own report group. Rewriting a
     comment in an applied migration changes nothing that runs; it's in
     the history the owner asked to cover (2026-10-22).
   - The report's groups: instructions (`AGENTS.md`, `CLAUDE.md`, Cursor
     rules), reviewers, skills, plans, ledgers, specs, other docs (audits,
     handovers, maps), code comments.
5. **Sections and anchors.**
   - The project's own headings stay, word for word. Each top-level
     section nests under the template section it belongs to, one heading
     level down; one that belongs to none stays as it is. GitHub's anchor
     is the heading's text, not its level, so no anchor changes, and
     Hatedate's `§3B` still resolves: only the file's name changes in
     `REQUIREMENTS §3B`.
   - A heading equal to a template heading (prizma's `## Done`) is that
     section, not nested under it.
   - prizma: Done → Done; Mandatory before launch → Next; its 11
     "Deferred review findings — plan N" subsections → Deferred review
     findings; Optional / nice-to-have → Later; Decisions to review stays.
     Hatedate: §0 → Now; §1, §2 → Next; §3 → Later; §4 → Done; its
     Changelog stays. The deepest heading after nesting is h5 (Hatedate's
     `#### From §1A`).
   - The H1 becomes `# Backlog`. The old intro paragraphs stay under it
     (prizma's rule for deferred findings, Hatedate's organisation note).
6. **Proving nothing was lost.** No new script. Every line of the old
   file, its heading marks stripped, survives in `BACKLOG.md`, except the
   H1:
   `diff <(git show HEAD:<old> | sed -E 's/^#+ //' | sort) <(sed -E 's/^#+ //' BACKLOG.md | sort) | grep '^<'`
   prints only the old H1. Then `git grep -n -F <old file name>` and each
   approved short name print nothing, and `git show --stat -M HEAD` shows
   the rename.
7. **The names in SSDD's own text.**
   - `SDD.md` is 10,990 of its 11,000-byte budget
     (`bin/repo.selftest.mjs`, "text budgets"). §3's "gets a home before
     the plan closes" becomes "gets a row in `BACKLOG.md` before the plan
     closes" (+15 bytes). §7's "Update the requirements/production
     checklist if the work affects readiness" becomes "Update `BACKLOG.md`
     if the work affects readiness" (−25). Net −10, to 10,980 bytes. No
     template link is added to §3; the ledger template names the file.
   - The ledger template's Follow-ups: "the requirements checklist" → "a
     row in `BACKLOG.md`".
   - `/new-reviewer`'s History: "the requirements checklist" →
     "`BACKLOG.md`".
   - The docs-sync reviewer's "Requirements / production-readiness
     checklist" (`reviewers/docs-sync-reviewer.md:22`), a fourth name the
     spec's Evidence missed, → "`BACKLOG.md`", and it adds "a deferred
     finding has its row". A reviewer reads it; nothing blocks on it.
   - The AGENTS template is 44 of its 45 lines; the Documentation Map's
     `BACKLOG.md` row takes the last one. The 5,000-byte install budget is
     at 3,994, and `/migrate-backlog` carries `disable-model-invocation:
     true`, so its description isn't counted.
8. **The security reviewer.**
   - It gains: a deferred finding's `BACKLOG.md` row names the problem and
     where it is, never the exploit path, since on a public repo the row is

   - Its threat-model citation (`reviewers/security-reviewer.md:13`) says

## Acceptance criteria

- **AC1 — The template.** `process/templates/backlog-template.md` has
  `# Backlog` and the sections Now, Next, Later, Deferred review findings
  and Done, in that order; the Deferred section's comment carries the row
  form and the public-row line.
- **AC2 — Seeding.** `install` on a repo with no backlog seeds
  `BACKLOG.md` from the template and records it in the lock's `seeded`;
  `update` from a lock without it seeds it too; an existing `BACKLOG.md` is
  never touched.
- **AC3 — Candidates.** With `docs/TODO.md` (or a root
  `X_REQUIREMENTS.md`, `release-checklist.md`), `install` and `update`
  seed nothing and print the candidate and `/migrate-backlog`; with two,
  both are named. `docs/a/b-checklist.md`, `requirements.txt` and
  `CHANGELOG.md` are not candidates.
- **AC4 — The names.** `SDD.md` §3 and §7, the ledger template,
  `/new-reviewer` and the docs-sync reviewer name `BACKLOG.md`, and no
  shipped file says "requirements checklist" or "requirements/production
  checklist". The AGENTS template's Documentation Map has a `BACKLOG.md`
  row. The text budgets still pass.
- **AC5 — The security reviewer** carries the public-row line and cites
  SSDD's `docs/limitations.md` for the threat model.
- **AC6 — `/migrate-backlog`.** The skill exists with
  `disable-model-invocation: true`, a description of at most 300 characters
  with no `": "`, and names its procedure: the report before any write,
  the lock's managed paths skipped, sections nested with their headings
  kept, rows moved with their words, short names approved one by one, the
  checks of Clarify 6, one commit.
- **AC7 — SSDD's own backlog** is `BACKLOG.md` at the root, every mention
  rewritten (`git grep -n 'docs/BACKLOG'` prints nothing outside this
  spec and its plan, which describe the move), and the links check
  passes.
- **AC8 — Scratch runs.** On scratch clones of prizma and Hatedate, the
  skill's report lists the rename, the section map of Clarify 5, the
  moved rows (prizma 64, Hatedate 0) and the mention groups with counts;
  applied there, the checks of Clarify 6 pass.
- **AC9 — Close.** CHANGELOG `## [3.5.0] — unreleased` with an Upgrade
  section that names `/migrate-backlog`, `SPEC.md`'s v3.5 row, the
  backlog's v3.5 item removed, and the full suite passing. VERSION becomes
  3.5.0 in the release commit, on the owner's go-ahead.
